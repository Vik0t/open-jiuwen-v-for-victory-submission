# Как устроен агент и что показали следующие варианты

Состояние на 8 ноября 2026 года. Выбран прежний алгоритм v3 с увеличенным
временем ожидания ответа модели. Более сложная v4 и её упрощённый вариант
не дали устойчивого выигрыша на новых задачах. Их код и результаты сохранены
для дальнейших исследований, но дополнительные механизмы не приписываются
выбранной поставке. Числа и условия сравнений — в [отчёте](../reports/agent_next_2026-11-08/report.md).

## 1. Что должен сделать агент

Нужно набрать максимальную сумму наград за правильные решения. Все задания
делят один запас токенов. Поэтому важно решить задачу, сохранить ответ и
не потратить весь запас на одну трудную программу.

Из `task.json` решатель получает только пять публичных полей:

| Поле | Значение для агента |
|---|---|
| `task_id` | Идентификатор задания |
| `task_type` | Код, математика, анализ данных или поиск |
| `instruction` | Условие: какой результат нужно получить |
| `reward` | Награда за верный результат; она не означает сложность |
| `check` | Способ проверки и требуемый формат ответа |

В `workspace` находятся исходники, таблицы и другие доступные материалы.
Ответ записывается в `answer.txt` рядом с `task.json`. Для кода сохраняются
исправленные исходники и ответ `DONE`; для остальных заданий — одна строка.
Открытые тесты видны агенту. Эталоны и закрытые тесты ему не передаются и
проверяют результат после завершения работы.

Изначальная идея предсказывать токены стала вспомогательной: главный результат
соревнования — баллы, а не точность прогноза. Даже более точная модель стоимости
полезна, только если помогает выбрать задачи и в итоге получить больше баллов.

## 2. С чего читать выбранный код

| Файл | За какую часть отвечает |
|---|---|
| [run_agent.py](../run_agent.py), `solve` | Локальные решения, порядок задач и вызов модельного цикла |
| [workflow.py](../submission/workflow.py) | Запуск локальных обработчиков через openJiuwen |
| [compact.py](../submission/compact.py), `run_task` | Короткий запрос к модели, исполнение действия и сохранение ответа |
| [editing.py](../submission/editing.py) | Проверка путей, точечная замена и запись Python-файла |
| [gateway.py](../submission/gateway.py) | Настоящий запрос через `ReActAgent` и `Runner`, получение расхода |
| [budget.py](../submission/budget.py) | Резерв перед отправкой и учёт фактического расхода |
| [executor.py](../submission/executor.py) | Ограниченное исполнение Python |
| [task_io.py](../submission/task_io.py) | Загрузка публичных полей и запись допустимого ответа |

В `solve` есть два этапа. Сначала строгие локальные обработчики пробуют решить
поддерживаемую арифметику, поиск и CSV без модели. `unsupported` означает,
что условие не распознано и его нужно передать модели. При `unknown`
обработчик не получил обоснованный ответ: данные отсутствуют, противоречат
друг другу или некорректны. Такая задача завершается без ответа и без модели.
Код сразу идёт модели.
Локальный обработчик не вызывает другую скрытую модель.

Затем оставшиеся задания сортируются. **В выбранной v3 любые некодовые идут
раньше кода.** Внутри этих двух групп меньшее значение
`(размер файлов + 4000) / max(награда, 1)` идёт раньше. Так простая эвристика
предпочитает маленькую задачу с большой наградой. Это не обученная оценка
сложности и не вероятность успеха.

Задачи обрабатываются последовательно. Общий предел ожидания всей работы —
3500 секунд. Отдельной очереди допроверок и возвращений к задаче в v3 нет.

## 3. Что происходит внутри одной задачи

`compact.run_task` делает до восьми модельных вызовов. Сначала он составляет
список файлов и читает начальные фрагменты: суммарно до 18 000 символов.
В очередной запрос входят условие, список файлов, текущие фрагменты и два
последних действия с результатами. Вся растущая переписка заново не передаётся.
Модель получает до 1536 выходных токенов на действие; ближе к концу бюджета
предел уменьшается.

Модель возвращает одно действие в JSON:

| Действие | Что делает программа |
|---|---|
| `read` | Читает указанный фрагмент файла внутри рабочей папки |
| `python` | Исполняет короткую программу и возвращает вывод или ошибку |
| `edit` | Заменяет единственный точный фрагмент изменяемого исходника |
| `write` | Создаёт или переписывает допустимый Python-файл |
| `answer` | Пытается сохранить итоговую строку |
| `abstain` | Завершает задачу без ответа с причиной недостаточности данных |

Например, в задаче о таблице модель может одним действием прочитать CSV,
посчитать сумму и вызвать `submit_answer(value)`. Этот помощник печатает
специальную пометку. Контроллер извлекает значение и сохраняет его, если
исполнение завершилось успешно и формат ответа допустим. Модель сама не
записывает `answer.txt` произвольной программой.

Для исправления кода небольшая замена автоматически запускает открытые тесты.
Если они проходят, v3 немедленно сохраняет `DONE` и заканчивает задачу.
Открытые тесты проверяют только известные случаи: их успех не доказывает
выполнение всех требований. Именно это оказалось важным источником ошибок.

После чтения в памяти v3 остаётся последний запрошенный фрагмент данного
файла. Общий объём фрагментов ограничен 24 000 символов. Полного объединения
фрагментов и устранения бесполезных повторных чтений в выбранной версии нет;
это проверялось только в следующем эксперименте.

Python ограничен временем, памятью, доступными действиями и объёмом вывода.
В измерениях модельный код запускается в отдельном Docker-контейнере без сети,
который видит папку одной задачи. Ключа модели в среде программы нет.
Хеши исходных данных и тестов сверяются после исполнения; их изменение
отклоняется. Автоматическое восстановление копий после неудачной допроверки
относится к экспериментальной v4, а не к v3.

## 4. Как учитываются токены и остановки

Конкурсная стоимость — `выходные токены + входные токены / 10`.
Внутри `Budget` используются целые десятые доли: `input + 10 × output`.
Например, вход из 1000 токенов и ответ из 200 стоят 300 конкурсных единиц,
или 3000 внутренних единиц. Расход всех отправленных вызовов складывается.

До отправки `Gateway` проверяет модель и выходной предел и просит `Budget`
зарезервировать цену: консервативную границу входа плюс максимальный выход.
После ответа резерв заменяется фактическими числами из `usage`. Экономия
выхода возвращается в доступный остаток. Медианный прогноз здесь не разрешает
обойти резервирование.

Если резерв не помещается, запрос не отправляется. Контроллер может один раз
уменьшить выходной предел и повторить локальную проверку. Если запрос уже
отправлен, но полный ответ с расходом не получен, цена считается неизвестной:
резерв остаётся, новые запросы блокируются. Это не бесплатный отказ.

Помимо общего бюджета v3 перед каждым следующим вызовом проверяет, не достигла
ли задача своего порога `max(15000, общий_бюджет_во_внутренних_единицах / 4)`.
Например, при общем запасе 20 000 конкурсных единиц порог равен 5000.
Это проверка между вызовами: один очередной ответ может перейти этот порог.
Строгое разрешение самого запроса всё равно задаёт общий `Budget`.

Каждый шаг проходит через настоящий `ReActAgent` и `Runner` openJiuwen.
Внутренний агент ограничен одной итерацией: внешний читаемый цикл управляет
действиями и сохраняет их результаты. В экспериментах использована одна и та же
Qwen3.8-27B без рассуждений. Разрешённые идентификаторы проверяются в `Gateway`.

Единственное изменение выбранной поставки относительно старой v3 — допустимая
пауза при получении ответа увеличена с 60 до 180 секунд; подключение ограничено
10 секундами. Это сетевые ограничения, а не общий предел длительности запроса.
Некоторые успешные вызовы занимали по общему времени 95–98 секунд.
Увеличенный предел даёт больший запас при медленном ответе. Изменение одинаково применено
к обеим сравниваемым политикам. Общий предел работы остаётся 3500 секунд.
Старые прерванные прогоны не переписаны и не включены как
полные измерения с известной стоимостью.

## 5. Какие добавления проверили и пока не приняли

Полная v4 меняла сразу несколько частей: сохраняла кандидата с копией
исходников, восстанавливала его после неудачной правки, объединяла фрагменты
файлов, делила работу на первый отрезок из четырёх шагов и отдельное продолжение,
затем автоматически допроверяла готовые ответы. Очередь учитывала награду,
грубую вероятность успеха и цену по типу задачи. Проверки отмены исполнения
и восстановления входных данных также относятся к этой реализации.

Её исходники зафиксированы [отдельно](../experiments/agent_next_2026-11-08/v4_blind40/source).
На сорока новых задачах при лимите 40 000 v4 получила в среднем 149,5 балла
против 145 у v3, потратив примерно на 73% больше. При лимите 20 000 — 140,5
против 141,5. Устойчивого превосходства не получилось.

[Разбор траекторий](../reports/agent_next_2026-11-08/failure_analysis40.md)
показал одну полезную некодовую допроверку: неверный ответ стал правильным,
добавились 7 баллов. Но суммарно допроверки в четырёх запусках стоили 40 986
единиц, а десять допроверок кода не внесли ни одной правки. Повторные открытые
тесты часто подтверждали прежний неполный ремонт; длинные проверки нередко
не помещались в допустимый формат действия.

Затем в [упрощённом варианте](../experiments/agent_next_2026-11-08/lean_follow20_io180/source)
убрали автоматическую допроверку готовых ответов, оставив память, откат,
распределение и один повтор при изменённых исходниках. На отдельном новом
наборе из двадцати задач при лимите 20 000 он получил 80 и 67 баллов против
82 и 79 у v3. Но при лимите 10 000 он выиграл оба повтора: 76 и 66 против
71 и 64, с меньшим расходом. Поэтому упрощённый вариант нельзя назвать хуже
при любом бюджете. Для основного ориентира 100 000 на сто задач выбрана v3:
это те же 1000 единиц на задачу, что и при 20 000 на двадцать. Порог
автоматического переключения по результатам этих двадцати не подбирался.

Отдельно проверили минимальную добавку к v3: запросить у API ответ формата
`json_object`, сохранив тот же протокол действий. На уже изученных сорока
задачах один запуск дал 146 баллов против 144 и расход 19 334,3 против
19 644,9. Заранее установленный порог для новой закрытой проверки — +10
баллов либо экономия 10% без потери баллов — не достигнут. Поэтому эта
добавка тоже не включена в выбранный код. Небольшую разницу одного запуска
нельзя считать доказанным улучшением. [Разбор](../reports/agent_next_2026-11-08/screening_report.md)
показал исчезновение четырёх ошибок протокола, но дополнительные баллы
получены на другой задаче, где у контроля ошибки формата не было.

Важно не смешивать проверку механизма с проверкой качества. Искусственный
HTTP-ответ может подтвердить учёт токенов, порядок действий и запись файлов.
Он не показывает, что настоящая Qwen стала чаще решать неизвестные задачи.
Тесты экспериментального отката не доказывают наличие отката в поставке v3.

## 6. Как проверяли прогноз стоимости

Отдельный [опыт прогноза стоимости](../reports/agent_next_2026-11-08/cost_model/report.md)
сравнил медианы, линейную регрессию Ridge и небольшой бустинг на тех же 28 группах.
Это отдельный опыт. В выбранной v3 нет ни обученного бустинга, ни
вероятностного распределителя из экспериментальной v4.

Вот что означают признаки в этом опыте:

| Признак в коде | Что именно измеряется | Зачем он может быть полезен |
|---|---|---|
| `task_type` | Одна из четырёх категорий из публичного `task.json` | Исправление программы обычно требует другой работы, чем извлечение короткого ответа |
| `instruction_bytes` | Размер условия в байтах UTF-8 | Длинное условие увеличивает видимый вход; байты не равны символам или токенам |
| `workspace_bytes` | Сумма размеров всех исходных файлов рабочей папки, кроме `__pycache__` | Показывает общий объём доступных материалов |
| `file_count` | Количество этих файлов | Много небольших файлов тоже требует навигации и чтения |
| `py_bytes` | Сумма размеров Python-файлов, включая открытые тесты | Грубая оценка объёма кода, который предстоит понимать |
| `table_bytes` | Сумма размеров CSV, TSV и JSONL | Грубая оценка объёма табличных данных; обычный JSON сюда не входит |

Например, для папки с двумя Python-файлами размером 2 и 3 КБ и CSV размером
5 КБ получатся три файла, около 10 КБ общего объёма, 5 КБ кода и 5 КБ таблиц.
Эти величины частично описывают одни и те же файлы: их не нужно складывать
повторно и выдавать за число токенов. Они доступны до запуска агента и могут
лишь косвенно указывать на объём работы. Эталонного ответа, будущих действий
или будущего расхода среди признаков нет.

Обучаемая величина — **измеренная цена первых не более четырёх отправленных
вызовов**, а не стоимость полного решения. Если агент остановился после двух,
учитываются два. Повторы одной задачи сначала усредняются. Проверка устроена
так: одно задание целиком откладывается, по оставшимся 27 строится модель,
затем прогноз сравнивается с расходом отложенного задания. Это повторяется
для всех 28 заданий. Медианы и преобразования тоже считаются только по
обучающим заданиям. Запрос с неизвестным расходом не заменяется нулём.

Средняя абсолютная ошибка означает, на сколько конкурсных единиц прогноз
в среднем ошибся без учёта знака. У медианы по типу она 290,28; у Ridge —
270,10; у бустинга — 252,78. Разница бустинга выглядит полезной, но разброс
на столь малом числе заданий допускает и ухудшение на других задачах.
Его веса в рабочий агент не установлены; рост баллов этим опытом не проверялся.


## 7. Как читать результаты и что проверять дальше

Прежние 28 задач — материал разработки. Сорок задач были новыми для полной v4,
но после анализа считаются знакомыми для следующих изменений. Упрощённую
политику проверяли на отдельно подготовленных двадцати. Повторы одной задачи
не превращаются в дополнительные независимые задания.

Инженерный пакет из ста задач объединяет 28 известных, 40 из предыдущей
проверки и 32 случая известных семейств. Он нужен для длинной очереди,
общего бюджета и времени; это не сто независимых новых задач. При лимите
100 000 и одинаковом сетевом пределе 180 секунд v3 получила 372 балла и 70 верных
решений из 80 выполнимых, упрощённая версия — 351 и 66. Их расходы составили
57 668,0 и 52 830,2. Это одна инженерная пара, не доказательство на новом финале.
При лимите 50 000 v3 получила 377 баллов и 70 верных решений, упрощённая —
322 и 62; расходы 49 195,2 и 48 224,7. Малобюджетное преимущество упрощённой
версии с двадцати новых задач на этом пакете не повторилось. Разница 377
против 372 у v3 не доказывает пользу снижения бюджета: это разные генерации
и одно измерение каждой пары.
В двух задачах
кода из сорока обнаружены неоднозначные требования закрытых проверок;
исходные баллы сохранены, влияние исключения этих задач посчитано отдельно.
Финал организаторов остаётся другой, официальной оценкой.

Выбранная поставка также [проверена в контейнерах](../reports/agent_next_2026-11-08/selected_v3_io180/validation.md)
Linux arm64 и x86-64: по пять сценариев с искусственными HTTP-ответами и
по 13 проверок исполнителя. Исходники образов совпали с выбранным кодом;
резервы закрыты, данные и тесты сохранены. Это подтверждает запуск и учёт,
а не дополнительные баллы Qwen.

Наиболее предметные следующие гипотезы: короткая проверка каждого явно
названного требования к исправлению; более надёжная передача программы без
обрыва JSON; остановка одинаковой ошибки при неизменившихся исходниках.
Каждую нужно сравнить с v3 при том же бюджете на ещё не изученных задачах.
Улучшение формата или прогноза принимается в агент только после проверки
итоговых баллов и расхода.
