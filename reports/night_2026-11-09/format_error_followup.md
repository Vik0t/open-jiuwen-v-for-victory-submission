# Ответ в JSON только для задач исправления программ

**Восемь запусков завершены.** У v4 зарегистрировано 19 ошибок разбора JSON в программных задачах, у v5 — 0. Средняя награда v5 выше на обоих бюджетах; общий средний прирост — **14,5 балла**. Один из четырёх парных результатов ухудшился, поэтому это не одинаковый выигрыш каждого повтора.

Проверен один заранее описанный вариант: v4 с параметром `response_format=json_object` только для `coding`. Подсказки, разбор действий, очередь, восемь действий и предел ответа 1536 не менялись. Для каждого бюджета выполнены два повтора обеих версий. Использованы только новые одновременные контроли `format64_v4_*`, а не прежние результаты `confirm64_*`.

План и условие допуска записаны до генераций: [format_followup_protocol.md](format_followup_protocol.md). Это повторные запуски на тех же 64 задачах, уже использованных при разработке v5. Они не образуют восемь новых независимых наборов. Результаты резервных 16 задач в этот документ не включены.

Средние измеренные расходы: при бюджете 64000 — 62194,35 у v4 и 56110,4 у v5; при бюджете 32000 — 31527,7 и 31460 соответственно. Здесь учитывается весь запуск, а не только ответы с ошибками JSON.

## Прямое изменение формата и косвенное влияние бюджета

По HTTP-квитанциям подтверждено: у v5 `json_object` запрашивается только для кода, у v4 его нет; для остальных типов значение отсутствует в обеих версиях. Одинаковое построение некодового запроса относится к **одинаковым истории, контексту и остатку бюджета**, а не к произвольным двум запросам разных запусков.

При **64000** все некодовые HTTP-запросы идут до первого программного запроса. Их средняя разница награды: математика `−5,5`, данные `0`, поиск `+1,5`, всего `−4`. Эти исходы внутри агента получены до применения нового параметра и не объясняются его прямым действием. Средняя разница программных наград — `+16`, общая — `+12`. При этом разный ранний расход на некодовые задачи меняет и бюджет, с которым агент приходит к коду; это тоже ограничивает точную причинную интерпретацию прибавки.

При **32000** очередь перемешивает типы. Меньший расход на ранний код может изменить число запросов и допустимую длину ответа поздней некодовой задачи. В r1 наблюдается именно различие охвата: `n2_044` у v4 не получила HTTP-попытки, а у v5 получила две и была решена; `n2_055` получила дополнительную попытку, но осталась нерешённой. Для `n2_043` предел первого ответа изменился с 287 до 1387 токенов, исход — с неудачи на успех. Это наблюдаемые факты, совместимые с посредничеством бюджета. Отделить экономию на коде от разного расхода предшествующих некодовых действий по этим повторам нельзя.

В r2 малого бюджета направление охвата обратное: `n2_044` у v5 уже не получила вызова, а у нескольких поздних задач пределы ответа ниже. Среди различий некодовых наград малого бюджета ранние задачи, начатые до кода в обеих версиях, дают `+16` суммой двух повторов; поздние дают в сумме `+1`. Поэтому ни весь некодовый прирост, ни все поздние расхождения не объявляются доказанным эффектом JSON-режима.

## Проверка расчётов и границы вывода

Счётчики получены только после готовности всех восьми `score.json`. Неразобранные ответы сопоставлены с сохранёнными HTTP-квитанциями. Второй способ сверки использует записанные ошибки разбора из наблюдений: наборы событий совпали. Для каждого отправленного запроса проверена цена `I + 10×O`, суммы совпали с итоговым расходом. Порядок запросов большого бюджета и настройка формата проверены отдельно.

Два повтора каждого бюджета показывают разброс, но не дают гарантии выигрыша на любой новой задаче. Итог этой серии — выполнение заранее записанного порога на разработочных 64 задачах. Исходники, подсказки, пороги и модели в ходе анализа не менялись; действия из ответов не исполнялись; новых запросов к модели не было.
