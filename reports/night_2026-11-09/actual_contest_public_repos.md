## 1. anchadekwi: экономный цикл с фиксированными приорами

Порядок — награда, делённая на фиксированную стоимость типа: math 250, data 350, search 400, coding 850. Есть бесплатные решатели и эвристики пропуска; наличие URL само по себе может объявить задачу невыполнимой. Дальше до пяти параллельных задач: сначала модель 35B без рассуждений, затем при достаточной награде/остатке одна попытка 27B. Лимиты ответа 550 и 750; расход на задачу ограничивается кратным приору. Обученного прогноза остатка здесь нет. [Планировщик](https://github.com/anchadekwi/openJiuwen-Challenge-2026/blob/3e59424c53c7c5bcbd52261c9bcefbc5d69bbd1f/harness/planner.py#L7), [точка входа](https://github.com/anchadekwi/openJiuwen-Challenge-2026/blob/3e59424c53c7c5bcbd52261c9bcefbc5d69bbd1f/run_agent.py#L87).

Вызов действительно пытается идти через openJiuwen Model.invoke, но при исключении может повториться прямым HTTP. Бюджет прибавляется после ответа. Предварительная проверка требует только min(max_tokens,250), не резервируя полный возможный расход параллельных вызовов. При отсутствии usage используются оценки по длине текста. Следовательно, неизвестный уже отправленный запрос может остаться неучтённым, а повтор — добавить реальный расход. Это вывод по коду, не результат запуска. [Клиент и бюджет](https://github.com/anchadekwi/openJiuwen-Challenge-2026/blob/3e59424c53c7c5bcbd52261c9bcefbc5d69bbd1f/harness/llm.py#L35).

Для coding в начальный контекст попадают только корневые .py не больше 6000 байт и вывод первого тестового файла; README туда не входит. Получить его инструментами можно, но это не гарантируется. История накапливает действия, вывод каждого инструмента обрезан; исходный снимок файлов не обновляется. После изменения исходника успех первого тестового скрипта немедленно возвращает DONE. [Контекст](https://github.com/anchadekwi/openJiuwen-Challenge-2026/blob/3e59424c53c7c5bcbd52261c9bcefbc5d69bbd1f/harness/agent.py#L240), [завершение](https://github.com/anchadekwi/openJiuwen-Challenge-2026/blob/3e59424c53c7c5bcbd52261c9bcefbc5d69bbd1f/harness/agent.py#L436).

Главная несовместимость с частью наших реальных задач: тест запускается как обычный файл Python, а не через discovery с проверкой числа тестов. Модуль, содержащий только классы unittest без вызова unittest.main, может закончиться кодом 0, не выполнив ни одной проверки. Для наших старых upstream-задач такая форма встречается. Здесь нельзя переносить «public PASS» как доказательство качества. Из собственных проверочных материалов найден только mock_proxy; README оставляет калибровку приоров как TODO, чисел независимой проверки нет. [Запуск тестов](https://github.com/anchadekwi/openJiuwen-Challenge-2026/blob/3e59424c53c7c5bcbd52261c9bcefbc5d69bbd1f/harness/agent.py#L140).

Полезная идея: малая первая попытка и явная оценка выгодности. Неподходящие для переноса механизмы: мягкая предварительная проверка бюджета, подмена неизвестного usage оценкой и завершение по коду выхода первого скрипта.

## 2. KozlovKV: простой обучаемый прогноз и рюкзак

Здесь прогноз реально используется. Для каждого типа и уровня модели стоимость равна base + per_char × длина очищенного вопроса. Во время запуска множитель корректируется сглаженным отношением фактического расхода к прогнозу. Ожидаемая ценность — reward × 0.9 × p_solve; рюкзак с шагом 25 единиц пересчитывается, затем запускается наиболее выгодная выбранная задача. Отдельно считается запас сверх прогнозов оставшейся очереди, которым оплачиваются дополнительные проверки. [Оценка расхода](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/estimator.py#L42), [рюкзак](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/planner.py#L103).

Коэффициенты действительно обучаются линейной регрессией по траекториям с запасом 15%. В опубликованной таблице coding/fast сейчас имеет постоянную стоимость 102.41 и p_solve=0.99; это характеристика его обучающих данных, не универсальная вероятность успеха на наших больших модулях. Скрипт обучения не показывает отдельного независимого разделения; вопрос по длине не описывает размер исходников. Это интересный простой соперник для нашего статического приора, а не готовая доказанная замена. [Обучение](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/tools/fit_estimator.py#L36), [коэффициенты](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/estimator.json).

Coding получает до четырёх попыток с пределами 600, 600, 4000, 1500, включая рассуждения и общий запасной агент. Специализированный решатель возвращает только изменённые определения Python; большие файлы сокращаются до узлов, упомянутых в ошибках, и связанных вызовов. Однако его конкретный prompt содержит код и ошибки тестов, а не README или полное условие. Для задач «исправить согласно README» можно потерять именно непокрытые тестами требования. Поздний общий агент способен читать шире, но до него ещё нужно дойти. [Решатель](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/solvers/coding_solver.py#L28), [отрывки](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/solvers/pycode.py#L322).

Есть ещё два существенных ограничения. При исключении или отмене вызова резерв просто освобождается; уже отправленный запрос может иметь неизвестный ненулевой расход. А без явной команды тестов выбирается первый корневой тестовый файл, исполняемый как скрипт. Его код 0 может дать DONE ещё до обращения к модели. Собственный tools/score.py использует такое же правило для coding — без testsRun>0 и закрытых проверок. [Исключения и usage](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/llm.py#L176), [выбор тестовой команды](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/harness/solvers/pycode.py#L37), [локальный оценщик](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/tools/score.py#L15).

Авторы сообщают 241/241 на сгенерированной сотне и 51/51 на 19 сложных случаях. Это их локальные результаты: набор 19 не опубликован, сгенерированные задачи и оценщик другие. В репозитории есть функциональные тесты, генератор и сводка траекторий; я их не запускал и не пересчитывал счёт. Эти числа нельзя сравнивать с нашими 408/433 или объявлять официальным результатом. [README](https://github.com/KozlovKV/openjiuwen-tasks-predictor/blob/a1981496b8ddbf5c9818f39d1ea3136b5e087763/README.md).

Полезная гипотеза для нас — маленькая линейная модель стоимости плюс сглаженная калибровка, проверенная против наших медиан. Сохранение полного контракта и строгий учёт неизвестного расхода должны остаться нашими.

## 3. AlfaGraph2000: прогноз продолжения и отбор проверок

Это наиболее развитый из просмотренных вариантов. Признаки до старта включают тип, длину условия, размер/структуру файлов, строки таблиц, функции, ветвления и тесты. Состояние после шагов добавляет расход, ошибки, чтения, запуски, правки, проверки, обрезанные и пустые ответы. Прогноз ищет до 24 соседних разных траекторий с тем же типом, моделью и лимитом; оценивает будущий расход, вероятность успешного окончания и эмпирическую 80-процентную границу. По умолчанию Docker выбирает задачи по отношению ожидаемых баллов к прогнозу оставшегося расхода. В коде есть и варианты рюкзака/MPC. [Признаки и состояния](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/forecast.py#L12), [прогноз](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/forecast.py#L125), [планирование](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/forecast.py#L204).

Реальный openJiuwen workflow соединяет локальный решатель, агента, проверку и сохранение. Модельные вызовы идут через AgentForge parser и AsyncOpenAI с явно переданным max_tokens и отключёнными скрытыми повторными запросами. Резерв — байты сериализованного запроса плюс запас и предел выхода. Неизвестный usage списывается полным резервом и отдельно отмечается uncertain_charge; работа может продолжиться. Это консервативная оценка, не измеренный фактический расход. Наш v3/safe вместо этого сохраняет неизвестный резерв и замораживает новые запросы. [Workflow](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/workflow.py#L35), [клиент](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/client.py#L68), [учёт](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/budget.py#L89).

Публичный PASS ставит кандидат DONE, но включённая в Docker отдельная проверка может спроектировать тесты по контракту и запросить разбор расхождения. Политика отбора проверок оценивает вероятность исправления, вреда и расход, выбирая положительное reward×(fix−harm)/cost. Для вреда задан минимум 1%. Это содержательная постановка вопроса «стоит ли ещё проверять», а не бесплатная гарантия. [Кандидат](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/agent.py#L153), [проверка](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/review.py#L394), [ценность проверки](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/review_policy.py#L84).

Ограничения по прочитанному коду:

- Начальный текст файлов кэшируется в session.user и после правок не пересобирается; старые группы инструментов вытесняются. Есть риск старого исходника в контексте после потери свежей истории. Наш safe-кэш эту проблему решает явным обновлением отрывков. [Состояние](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/agent.py#L228).
- До отложенной проверки кандидат может находиться только в памяти: отчёт пишет awaiting_review с answer=None. При отмене уже начатой проверки оригинальный кандидат сохраняется; но принудительная остановка до её очереди не имеет общей финальной выгрузки всех кандидатов. Это условный риск по статическому пути, без экспериментального воспроизведения. [Сохранение](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/harness.py#L264), [отмена](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/harness.py#L365), [finally](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/harness.py#L525).
- Исходные тесты проверяются по хешам и реально обнаруживаются с testsRun>0. Это сильнее первого тестового скрипта, но успех публичных тестов по-прежнему не равен выполнению всего контракта. [Проверки](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/alfagraph/execution.py#L75).
- В README указаны внешние обучающие наборы и один опыт 173/235 против 167/235 при 81.9K против 99.6K. Там же честно сказано, что преимущество над простым поисковым отбором не установлено, а ответов на невыполнимые стало 10 против 4. В просмотренном дереве есть обученные профили, но нет полного набора/журналов/скриптов воспроизведения этих обучающих и контрольных опытов. Официальный результат не установлен. [README](https://github.com/maxim283b/openJiuwen_hack_AlfaGraph2000/blob/8b12bb1aefa8c877e0342eb74de9d46a9972ee86/README.md).

Полезно разделение «сколько ещё потратим», «с какой вероятностью исправим» и «можем ли ухудшить». Переносить большой контроллер с новыми слоями на основании одного чужого опыта оснований нет.

## Что это меняет в сравнении с нашим кодом

Проверены именно текущие исходники и четыре замороженные safe*-копии; все совпали со своими frozen source. Скрытые задачи для этого не читались.

| Механизм | Текущий v3 | Замороженные safe* |
|---|---|---|
| Порядок | Бесплатные точные обработчики, затем coding в конце и размер/награда | safe сохраняет порядок; safe_priority пробует reward×эмпирический успех/медиану стоимости |
| Предсказание | Обученный прогноз не управляет решением | safe_priority использует старые измеренные приоры, не новую модель по тексту |
| Жёсткий бюджет | I+10O, резерв до отправки, неизвестное держит резерв и замораживает работу | Дополнительно проверяются собственные пределы запроса; потенциальная ёмкость параллельности 3 вместо 5 |
| Контекст | Текущие отрывки; известные слабости порядка вытеснения и обновлений | Исправлены повторное чтение, согласованные срезы, обновление исходников, удаления и индекс |
| Завершение coding | Public PASS может закончить задачу; старый Python autoDONE не проверяет returncode | safe требует exit0 для Python autoDONE; safe_contract добавляет напоминание; safe_review убирает два autoDONE, но явный DONE остаётся решением модели |

Оба run_agent остаются последовательными; ёмкость Gateway/Budget сама по себе не делает три/пять сессий. В проекте есть schedule.choose_tasks с рюкзаком, но основной run_agent.solve его не вызывает. Наличие файла с алгоритмом не следует описывать как внедрённое поведение.

Реальные сильные стороны нашего пути: строгая проверка числа и результата тестов, отделение неизвестного расхода от фактического, передача README и текущего состояния файлов, сохранение уже принятого ответа. Слабое место publicPASS уже обнаружено отдельно; одно лишь слово «проверка» в промпте не доказывает полного покрытия требований.

## Гипотезы без изменений runtime

1. Сравнить маленький прогноз стоимости с длиной/размером файлов и онлайн-поправкой против наших медиан; истинное качество измерять отдельно от заявления агента об успехе.
2. При уменьшении контекста coding сохранять README и все названные части API, а не только место публичной ошибки. Исправленный safe-кэш не жертвовать ради короткой истории.
3. Прогноз расхода использовать для выбора, резерв — для ограничения. Не переносить освобождение неизвестного уже отправленного запроса.
4. Сначала проверить простую выборочную проверку против отсутствия проверок при одинаковом бюджете, включая вред и потери готовых кандидатов. Сложное обучение по редким улучшениям — следующий отдельный опыт.
5. Сохранить обязательный testsRun>0 и воспроизводимые проверки failed assert/явного DONE: чужие идеальные локальные цифры с другим оценщиком не заменяют их.

Это идеи для наших старых разработческих данных, не повод открыть свежие 32/64 или скопировать чужой код. Ничего из найденного не внедрялось.
