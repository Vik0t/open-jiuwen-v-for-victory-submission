# План ночной проверки, 8–9 ноября

Работа ведётся до 08:00 9 ноября по Новосибирску. Цель — увеличить сумму
наград при том же общем бюджете, сохранив простой код и воспроизводимость.
Текущая контрольная версия — точная v3 IO180. Её архивы не изменяются.

## Что уже известно до новых запусков

На старом инженерном наборе основные потери сосредоточены в коде и математике.
Повторные проверки всех готовых ответов оказались дорогими. В одном случае
шесть одинаковых правок без изменения исходника потратили 4134,7 единицы.
Номер текущего шага и оставшийся лимит модель не видит. Эти наблюдения
получены на разработочных данных и не считаются новым подтверждением качества.

## Порядок опытов

1. Проверить официальный шлюз на четырёх допустимых моделях и точный учёт
   входных, выходных и включённых в выход рассуждающих токенов.
2. Сравнить прежний алгоритм на Qwen27 и Qwen35 без рассуждений.
3. Отдельно проверить короткое сообщение об оставшихся действиях и явную
   ошибку при правке, которая не изменила исходник.
4. Затем проверить 12 вместо 8 действий для кода. Отдельной очереди или нового
   агента для этого не требуется.
5. Для математики отдельно проверить простые граничные случаи до основного
   расчёта и доступ к точной математической библиотеке. Сторонние классические
   пакеты разрешены регламентом, если установлены при сборке; ограничения
   зависимости конкретной задачи сохраняются.
6. По результатам обзора сильных открытых агентов выбрать следующие небольшие
   изменения. Каждое сначала проверять отдельно, без массового объединения.
7. Зафиксировать лучший кандидат до просмотра нового закрытого набора;
   сравнить с контролем на одинаковых задачах, бюджете и моделях. Если
   меняется модель, отдельно показать выигрыш модели и выигрыш контроллера.

## Условия проверки

- Прежние 28, 40, 20 и инженерные 100 теперь служат для разработки. Новый
  прогон знакомых задач не называется независимой проверкой.
- Для длинного инженерного запуска: 100 задач, общий лимит 100000, затем
  при необходимости 50000. Один повтор позволяет отбирать гипотезы,
  но не доказывает устойчивого выигрыша.
- Официальный доступ использует суффикс `-noreason` для отключения рассуждений.
  Параметр DeepCode `enable_thinking:false` на официальном сервере не действует.
- Выбор модели, источник кода, среда исполнения, параметры, порядок задач,
  исходные данные и проверяющий фиксируются до запуска. Старые снимки
  не исправляются задним числом.
- Сервис разрешает три одновременных запроса; начинаем с двух последовательных
  потоков. Лимит сервиса в запросах отделяется от конкурсного бюджета в токенах.
  После проверки фактической нагрузки допускается третий поток; при этом
  отдельные диагностические генерации не запускаются. Наблюдаемый RPM остаётся
  ниже 120, каждый прогон сохраняет свой независимый токеновый бюджет.
- Сгенерированная программа исполняется только в изолированном контейнере
  без сети и ключа API. Дополнительные проверки доступны только проверяющему.
- Отправленный запрос без полного `usage` остаётся с неизвестным расходом.
  Резерв не освобождается, автоматической повторной отправки нет.
- Никаких покупок, локальных нейросетей или публикации репозитория в ходе опытов.

## Решение о выборе

Основной критерий — итоговые баллы при одинаковом лимите, затем фактическая
стоимость. Число пройденных открытых тестов само по себе недостаточно.
Новые гарантии проверяются небольшими воспроизведениями; пользу для качества
проверяем настоящими запусками. В итоговой документации отдельно перечисляются
внедрённые изменения, не подтвердившиеся идеи и оставшиеся ограничения.
Устойчивый скачок требует новых задач и повторов: один удачный запуск
или выбор лучшей строки нескольких таблиц его не устанавливает.

## Вторая серия: повторяемость простых политик

До первого результата этой серии зафиксированы четыре политики: `safe_source`,
`safe_contract_source`, `safe_review_source`, `safe_priority_source`.
Общее основание: исправления памяти фрагментов и кода завершения Python,
проверка отдельных границ расхода, предел три одновременных запроса.
Принудительный JSON отключён: первый выигрыш 408 не подтвердился вторым
запуском 374; среднее 391 против 392 у двух контрольных повторов.

Для каждой из четырёх политик назначены три запуска инженерных ста задач
с бюджетом 100000. Добавлен третий повтор исходного контроля. Полный список
13 запусков записан в `phase2_batch.py` до их начала. Серия использует не
больше трёх потоков API и прекращает выдавать новые задания серии при
неизвестном расходе или ошибке. Проверки функциональных свойств до запуска
сохранены в `phase2_verification.json`; это не показатели качества модели.

Следующие небольшие гипотезы остаются частью разработки: исходный результат
public tests до первого обращения (`grounded_contract_source`) и формирование
исполняемых проверок требований до правки. Их код также фиксируется перед
генерацией. Нельзя выбирать лучший отдельный повтор или выдавать результаты
этой серии за независимую проверку.

## Новые наборы и граница независимой оценки

Условия и ответы первого32 и второго64 root не просматривал. Авторы наборов
не меняют контроллер по известным им ответам. Награды назначены независимо
от сложности. Все программы и проверки исполняются в строгом контейнере.

До первого акторского запуска первого32 исправлен общий интерфейс оценщика:
он ошибочно запрещал новые вспомогательные и выходные файлы. В отдельной
копии `agent_night_holdout_v2_2026-11-09` они разрешены в соответствии с
инструментами; данные и тесты из условия защищены. Условия, эталоны и награды
не менялись; исходная копия сохранена. Новый оценщик проверен эталоном,
пустым решением и независимыми фиксированными примерами файлового интерфейса.

Первый32 можно использовать для выбора между заранее зафиксированными
кандидатами; в этом случае он называется проверочным набором разработки,
а не окончательным независимым подтверждением выбранной по нему политики.
Основной кандидат для второго64 выбирается и фиксируется до чтения его
результатов и условий. Предварительные уровни бюджета: 32000 и 16000 для32;
64000 и 32000 для64. Контроль и кандидат получают один и тот же бюджет,
модель и среду. План — не меньше двух повторов каждой основной пары.

Допустимый математический пакет SymPy проверяется отдельно от изменения
контроллера, если эта гипотеза будет перенесена на новые задачи. Старый
математический опыт не показал прироста правильных решений; его различие
расхода пока нельзя считать надёжным выигрышем. При сравнении среда с пакетом
должна быть одинаковой для соответствующего контроля и кандидата.

## Четвёртая серия: требования и понятные ошибки

До начала генераций зафиксированы две версии: `raw_spec_source` и
`raw_spec_simple_source`. Они читают README один раз и показывают исходный
текст требований непосредственно после условия на каждом шаге. Этот блок
не вытесняется памятью фрагментов; увеличенный вход полностью учитывается.
Прежние фрагменты файлов пока сохранены, чтобы не смешивать два изменения.
Первая версия содержит начальную диагностику публичных тестов, вторая — нет.
Для обеих назначены два повтора старых100 и один запуск выбранных старых5.

Отдельно проверяется `plan_feedback_source`: ошибочная программа собственных
проверок отклоняется ещё при принятии плана; ошибка указывает действительную
строку. Сначала два запуска старых5, затем решение о дальнейшем опыте по
среднему результату, а не лучшему повтору. Полный список записан до запуска
в `phase4_batch.py`. Все три предыдущих потока должны закончиться прежде,
чем начнётся эта серия.

Следующая небольшая гипотеза — несколько точных замен одного исходника в
одном действии. Нынешний агент завершает задачу сразу после первой правки,
прошедшей публичные тесты; это может оставить второй явно описанный дефект.
Новый формат должен позволить применить все необходимые замены вместе, без
дополнительного обращения и без обязательного написания собственных тестов.
Сначала проверяются целостность исходника при ошибке и совместимость старого
формата. Выигрыш в закрытых тестах до реального сравнения не заявляется.


## Проверочный набор32: правила до первого запуска

Для выбора политики зафиксированы восемь вариантов: контроль v3; тот же
короткий решатель с общими исправлениями исполнения; явный README; пакет
точных замен; два прохода4+4; один отложенный отзыв после первичного охвата;
очередь по средней цене и вероятности; полноценный обычный ReAct.
Имена val32_*, бюджет32000/16000, по два повтора каждого варианта.
Все16 снимков подготовлены до первого запуска на этих задачах.

Основной критерий выбора — средние баллы четырёх запусков, с равным весом
двух бюджетов и повторов. При равенстве — меньше измеренный расход, затем
проще код. Оба бюджета также показываются отдельно: среднее не должно
скрывать разный характер результатов. У обычного ReAct сохраняются настоящая
история SDK, пять инструментов,12 итераций и выходной предел2048; у короткого
цикла —8 действий и1536, кроме отдельно указанного4+4. Это сравнение политик
при одном общем ресурсе, а не заявление о различии ровно одного параметра.
Для переноса обычного ReAct в поставку понадобилась бы отдельная интеграция;
его сравнительный адаптер зависит от зафиксированной программы испытаний.

Общие исправления у новых кандидатов: настоящий __main__ и чистый argv,
строка виртуального исходника в traceback, защита доверенного родителя,
запрет изменения прав/владельца в дочернем Python. Старый контроль v3 оставлен
без изменений. Исходники и ответы32 root до этого момента не просматривал;
после выбора по его результатам этот набор считается разработочным.
Наборы64 и резервный16 остаются для последующей независимой проверки.

Перед этим первая серия4b остановилась на HTTP429 без usage. Резерв3475,6
не освобождён; известный расход прерванного запуска3207,3. Он не считается
полным качественным сравнением или бесплатным запуском. Другие два уже
отправленных опыта завершились и сохранены; оставшиеся задания серии не
запускались. /limits после инцидента разрешает запросы, объёмная квота
не исчерпана. Следующая серия ограничена двумя, а не тремя потоками.
Существующие результаты и снимки не перезаписываются, неизвестный запрос
автоматически повторно не отправляется.
