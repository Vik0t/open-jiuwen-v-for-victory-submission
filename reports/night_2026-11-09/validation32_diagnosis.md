# Что показали 32 проверочные задачи

Это разбор раскрытого **validation32**, теперь используемого для разработки, а не официальный результат или независимый тест. В каждом прогоне 32 задачи, из них **26 решаемых; максимум 138 баллов**. Ещё шесть нерешаемых предусматривают отказ и учитываются отдельно.

Проверена готовая сводка `val32_core_complete_checked.json`: восемь вариантов, два бюджета, по два повтора — **32 прогона**. Все расходы известны, неизвестных запросов и удержанных резервов нет. Расход измеряется как `выходные токены + входные/10`, в тех же единицах, что бюджет. Средние ниже — только по двум повторам, без оценки статистической значимости.

При B32k пакетные правки дали **+19.5 балла в среднем** при почти одинаковом расходе: 30 195.2 против 30 185.4. Разложение баллов: код **+16**, математика **+6.5**, данные **−3**, поиск **0**. Число `budget_unavailable` нельзя считать числом задач без попытки. В common/r1 таких программных строк пять, но **только четыре имеют 0 HTTP и нулевой расход**. Пятая, `night_003`, сделала три платных запроса стоимостью 2270.4. Баллы непопробованных задач — лишь потолок эталона, не гарантированный выигрыш.

В common/r1 математика заняла 10 091.5; одна правильно решённая задача — 7082.4. В batch/r1 она обошлась в 1507.4. Это нельзя приписывать пакетному редактору: он меняет только программные инструкции. Непрограммные задачи и механизм начального промпта прежние; ответы, дальнейшие истории и остаток расходятся. Полный исторический промпт не сохранён: побайтное совпадение всех последующих запросов не заявляется. SDK отправляет temperature=0; причину разброса это не устанавливает.

При B16k **ни common, ни batch не начали ни одной из восьми программных задач**. Разница 91 против 86 баллов возникла в непрограммной части и охвате; это не проверка качества пакетных правок при малом бюджете.

Обычный ReAct при B32k решил по типам: код 1/0, математика 1/1, данные 3/3, поиск 2/2. Средний расход соответственно 15 828.9, 1928.0, 5718.5, 6235.1. Без HTTP осталось 15/16 решаемых задач: слабый охват при дорогих программных попытках. Вывод относится к этому контролю, а не любой реализации ReAct.

## Потерянные действия и неполные исправления

В batch/r1 при B32k действительно выполнены **6 пакетных действий и 10 замен**, все шесть прошли публичную и полную проверку. Однако остались четыре ответа, которые строгий разбор не принял: **547, 634, 43, 43 выходных токена**, каждый с `finish_reason=stop`, а не `length`. Общий расход этих ответов — 2725.9; действие из них не исполнилось.

1. **`night_006`: потеря формата.** Дважды пришла одна и та же вводная фраза, затем полный корректный JSON чтения файла. Это два потерянных действия стоимостью 852.0. После четырёх оплаченных запросов задача остановилась по бюджету. У двух длинных ошибочных ответов полного единственного объекта после префикса нет: простое снятие вводной фразы их не исправляет.
2. **`night_008`: неполный контракт.** common в обоих повторах исправил копирование заголовков лишь в конструкторе. README также требует обновление из другого объекта и добавление именованных аргументов после исходных значений. Эти ветки не исправлены. Два публичных теста проходят, агент сохраняет DONE, полная проверка провалена. batch прошёл её в обоих повторах.
3. **`night_007`: исправлен помощник, забыта связь вызовов.** common/r2 добавил помощнику параметр имени опции с пустым значением по умолчанию, но прежний вызывающий код имя не передаёт. Поэтому требование сохранять строки для перечисленных имён фактически не работает. Публичные тесты проходят, полная проверка нет. batch/r1 изменил три связанных фрагмента за одно действие и прошёл проверку; r2 тоже успешен.

Отказ разбора не меняет программу; частичная правка может ошибочно завершиться после узких публичных тестов. Ответы эталона как алгоритм не использовались.

Обе оплаченные проверки касаются `night_008`. В обоих случаях ответ обрезан с `finish_reason=length`, JSON не разобран, действие не исполнено, `review_kept=false`. Остальные строки проверки закончились без HTTP по бюджету. **Успешных проверочных правок нет.** Поэтому 124/119 баллов нельзя приписать исправлениям после первичного обхода: первые проходы разных запусков сами дали разные результаты. Отдельный балл первого прохода не реконструировался и не переоценивался; непроверяемую реконструкцию не добавляем.

## Что уже установлено и что ещё проверяется

- Представление «пакетные правки одинаково полезны при любом бюджете» не подтверждено: выигрыш виден при 32k, а при 16k до их применения дело не дошло. Причинный вклад в код нужно отделять от случайной непрограммной разницы.
- Объяснение высоких баллов review успешной допроверкой **опровергнуто квитанциями**: принятых исправлений ноль. Сама идея допроверки при достаточном остатке этим ещё не опровергнута.
- В уже запланированных phase5b/5c проверяются точная математика с контролем на том же образе, охват всех типов за 2+6 действий, их сочетание с пакетной правкой и два альтернативных формата JSON. По снимку на 05:20 НСК phase5b завершено 9/12, два запуска идут; phase5c ещё не начата. Незавершённые результаты не подмешаны в таблицы. Повторное использование validation32 уже не даст независимого подтверждения качества.
